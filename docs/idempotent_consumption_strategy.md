# 文档异步链路幂等消费策略说明

## 1. 文档目的

本文档用于说明本系统在 Kafka 异步链路中的幂等消费策略，回答三个核心问题：

1. 重复消息为什么一定会出现。
2. 系统如何在保证消息不丢失的前提下，做到业务只处理一次。
3. 为什么本系统需要本地消息表 (Outbox) + 任务账本 + 消费日志，而不是只用 Redis 去重 key。

本文档只描述逻辑和约束，不包含具体代码实现。

## 2. 适用范围

当前策略覆盖文档处理模块的四类消息：

1. `doc-parse-request`
2. `doc-vectorize-request`
3. `doc-delete-request`
4. `doc-dlq`

对应业务阶段：上传后解析、解析后向量化、删除补偿、死信集中处理。

## 3. 设计目标

> **真实场景例子**：
> 如果用户“张三”上传了一份 50 页由财报合并而成的《合并报表.pdf》，因为界面卡顿，他连续点了两次“上传”。我们的最终目标是：系统底层只保存一份文件，耗时几分钟的文档智能解析也只跑一次，Elasticsearch（ES）索引里不能出现两份相同的段落。而且，在这些动作中哪怕服务器中途断电重启了，进度也不会丢。

1. 业务与消息最终一致：业务已提交的事件必须最终可投递。
2. 消费幂等可验证：同一 `message_identity` 不论是在故障重发、重新执行还是重复投递等情况下，最多只会产生一次有效的数据写入。
3. 重复投递支持安全地重复处理：重复到达的无效消息，要么能被安静跳过，要么能按既定轨迹重新挂起，绝不能改乱已有数据。
4. 并发消费可控：同一个任务消息，在同一时刻最多只能允许一台服务器处理。
5. 失败可恢复：失败后能按流程重试、排查得出原因、并且能重新追踪到异常源头。
6. 结果可审计：通过账本随时能回答“谁处理了什么文件”、“跑了几次”、“为什么失败或者被跳过了”。

## 4. 核心策略总览

> **真实场景例子**：
> 在咱们的 AgenticRAG 中，解析 PDF 需要调外部 MinerU API（很费时），切分后还需要调大模型算向量然后写到 ES（又耗算力又慢）。因为耗时久，中间断网、执行超时、机器重启的概率会大增，所以如果只拿个普通 Redis key（例如 SETNX）来挡重复，一旦缓存服务器崩了、或者时间设错提前过期了，同一个 50 页文档就可能引发多次昂贵的重复处理。于是我们需要在所有容易出事故的关节（即“生产发送”、“消费加锁”、“业务检验”、“结果入库”四层）套上防护网。

系统采用四层协同防漏机制，而不是单点去重：

1. 生产端确保一定能发出去：用数据库做事务型的“本地消息表 (Outbox)”。
2. 消费端上锁排他：用 `mq_consume_log` 的独占获取和带有效期的租约。
3. 业务层再防二次重入：处理前还要靠“文档当前在各个阶段的状态机”作前置检验。
4. 结果层确保状态统一更新：成功/跳过/失败统记录入库，全做完了再去向 Kafka 点“消息确认”。

四层缺一不可。只做一层或者漏做一层，都会导致消息处理在某种极端断网下重重叠叠。

## 5. 端到端消息生命周期

### 5.1 生产阶段（Outbox 模式与留痕策略）

> **真实场景例子**：
> 张三点击上传，后台 MySQL 的 Document 表里存下了一笔文档数据，顺手就在 Outbox（待发送消息表）里存下了一条【要去解析】的通知。“上传成功”按钮刚变成绿色，应用服务器电源被踢掉了，此时这则通知根本没进 Kafka 队列。但没关系啊！因为 MySQL 数据不会丢，等服务器一开机，后台守护程序一扫表，就把没发出的通知继续丢进 Kafka，确保后台工作继续转！发出去之后，系统也不会把这条写着“已发送”的记录立刻毁尸灭迹，而是留着它作为后续谁也赖不掉的“发件底单铁证”。

1. 在业务事务内写入业务表和本地消息表 (Outbox) 记录（初始状态为 `PENDING`）。
2. 提交事务后，由 Dispatcher 定时或基于事件去扫描数据库，**通过索引只精准捞取** `PENDING` 或待重试的 `FAILED` 记录。
3. Dispatcher 发送消息至 Kafka。
4. 发送成功后本地消息表 (Outbox) 仅把记录标记为 `SENT`（并记录 `sent_at`），**坚决不要用“阅后即焚（发完立刻删除）”的做法**。
5. 发送失败则写回 `FAILED`，并按指数递增的时间间隔计算下一次发送时间的 `next_retry_at`。

#### 5.1.1 为什么保留海量 SENT 记录不会拖垮数据库？（性能论定）

既然要“留底单”，就意味着表里必然堆积大量 `SENT` 数据。为了在不删数据的情况下榨取最高性能，系统底层与业务代码强依赖以下全方位适配：

1. **利用 B+Tree 索引斩断扫描（SQL 架构层）**：
   数据库表已建立复合索引 `INDEX idx_outbox_dispatch (status, next_retry_at, id)`。在 B+Tree 物理结构中，第一层会按 `status` 严格分区聚簇。
   业务代码的拉取 SQL 必须精准限定 `WHERE status IN ('PENDING', 'FAILED') AND next_retry_at <= NOW()`。优化器会顺着树根直接跳至 `PENDING` 区块扫描，**物理级别彻底绕开百万千万级的 `SENT` 大山**。不删数据，对当前排队拉取速度毫无影响。
2. **并发争抢隔离（业务代码层适配）**：
   多台应用服务器同时拉取 `PENDING` 数据时必定引发锁冲突。业务层在 MyBatis/JPA 执行拉取时，必须适配 MySQL 8.0+ 的行级游标跳过隔离语法：`SELECT * FROM mq_outbox WHERE ... LIMIT N FOR UPDATE SKIP LOCKED`。谁拉到了任务，该记录就对其他机器“隐身”，避免了查询堵塞和重复派发。
   <!-- TODO -->
3. **状态类型瘦身（SQL 优化演进方向 TODO）**：
   当前结构中 `status` 使用了 `VARCHAR(32)`，在 B+Tree 比对时体积较大。未来架构升级时可降维为 `TINYINT` 映射（如用数字 2 代表 SENT），压缩单行索引体积，降低树高，提升内存页的极速命中率。
4. **生命周期归档策略（兜底方案）**：
   查询不慢，不代表物理硬盘容得下。系统不“阅后即焚”，但需要配备定时归档批处理 Job：在凌晨低峰期将 `sent_at` 早于 15 天的旧证据数据导入 `mq_outbox_history` 冷库，并物理清除主表记录，解决表空间无限膨胀的存储负担。

结论：既保障即使发生断网消息也不会无影无踪，也保证了后期追踪扯皮有据可查。凭借“B+Tree 索引状态裁剪”、“SKIP LOCKED 并发规避”以及“冷热归档兜底”，这套保留证据的重型打法做到了逻辑完整与性能自洽。

### 5.2 消费阶段

> **真实场景例子**：
> 服务器前台收到了通知，将它发给处理节点 A。节点 A 开始花 3 分钟解析《合并报表.pdf》。过了几十秒，因为网络闪断，Kafka 以为节点 A 挂了，把这条解析通知转给备用的节点 B 重试。结果节点 B 刚领到任务，一查数据库 `mq_consume_log`，“啥？节点 A 已经拿了尚在有效期的大锁，正在吃吃吃吃干着！”节点 B 便乖乖返回告诉消息系统“等下再说（RETRY_LATER）”。这就避免了两台高配置机器一起死磕同一份大文件。

1. 系统拿到消息后先计算唯一的 `message_identity`（给事情做“防伪标识”）：
   1. 优先使用原本的业务记录 `messageId`。
   2. 缺失时退化为主题 `messageKey + 本次负载内容的整体哈希值`。
2. 按照 `(所属的小组, 队列名称, 消息防伪标识)` 这个组合去尝试向系统声明“这活儿我包了（独占获取权）”。
3. 认领结果只会有三类：
   1. `PROCESS`：系统说行，这活归你办。
   2. `ALREADY_COMPLETED`：系统一查说：这活早就干完了，该消息作废跳过并去打个勾（确认）。
   3. `RETRY_LATER`：别的节点正端着大锁在运行这事儿呢，您晚点再来问。
4. 只有在前边业务彻底忙完并把结果数据改完了，我们才会去向 Kafka 手动点击“消息确认”。

结论：同一档子事，不管Kafka重发多少次，真正耗时耗力的解析业务不会重复跑，也不会出现同时在两台机器上打架的情况。

## 6. 幂等决策模型

> **真实场景例子**：
> 这个机制的目标，就是即使情况千变万化——比如由于超时而让消费自动重新进队列了，再比如某个运维大哥为了补这批跑偏的文档，后台连点了七八下强制回放——在代码眼里它们都是：同一个动作引发的消息重发。认出了它是谁，才能做出正确的避让。

### 6.1 唯一键模型

消费唯一键：

`consumer_group + topic + message_identity`

该唯一键用于把“同一个业务动作的任意反复重发”最终合并为只生效一次的有效处理。

### 6.2 状态模型

消费日志状态主要分4种：

1. `PROCESSING`（进行中）
2. `SUCCEEDED`（搞定了）
3. `FAILED`（真出错了）
4. `SKIPPED`（不需做，跳过了）

这里的 `PROCESSING` 千万不能是个光秃秃的状态，它必须带上个打工倒计时的租约时间 (`locked_until`)，在这个时间内其他人绝对不充许插手。

### 6.3 决策语义

1. 日志里发现曾经这条已显示跑到 `SUCCEEDED` 或者 `SKIPPED` 了，就证明它曾经成功过：立即返回 `ALREADY_COMPLETED`。
2. 日志里显示虽然处于 `PROCESSING` 但是倒计时还没结束：立即返回 `RETRY_LATER`（改天吧别添乱了）。
3. 如果压根还没这个日志，又或者那倒计时实在太久远早就到期作废了：立即返回 `PROCESS` 收归己有。

## 7. 业务侧二次防线（拦截又慢又贵的 I/O 动作）

> **真实场景例子**：
> 万一 Kafka 通知真因为一些我们不了解的诡异 Bug 绕开了上述防锁拦截（运气坏到极点）。当代码辛辛苦苦拿着文本开始一块块调向量算力、正准备写到 Elasticsearch 库里的 300 个节点块时，它还会使出一招“破釜沉舟”：我要写 101号 文档对吧？行，写入以前我先给 ES 发一句——“DELETE BY 查询条件：所有的 101 号”，哪怕之前错写过半截子内容，也在这 一刻被冲刷的干干净净了。搜出来的永远只有这一回刚热乎入库的数据！

只做外围的消息去重有时候还有薄弱点，涉及到掏钱耗时的重逻辑还要再加上 一层安全衣。

### 7.1 向量化阶段防重操作

1. 如果看到文档本身状态已经挂上了 `VECTORIZED` 状态标签：那干脆无视，马上跳过。
2. 如果看到文档状态栏写着正被 `PARSING`（前置节点还在抢修），那我们自然也要跳过或稍后再试。
3. 最暴力也是最有效的防重：在准备向 ES 写一堆分片数据时，先把原来关联这个 `documentId` 以及租户归属的老分块全套清空一下，然后我们再放心大胆地插入新的那批。

这目标很简单：不让用户的知识库里被查出来两遍重重叠叠的语段内容引发系统“抽风”。

### 7.2 删除阶段防重操作

1. 业务已经处理完删除了，Kafka删除消息又跟抽风一样再传了一遍过来。我们看看任务账本判定一下“这货早就被删了”。
2. 对本就完成的事安全跳过不报错，省得弄得日志一堆大红色的 ERROR 报错。

## 8. 为什么老有人说“给个 Redis 去重 Key不就行了？”

> **真实场景例子**：
> 如果咱们是做给文章“点个赞”，加个 10 秒过期的 Redis 确实轻巧完美。但咱们现在是在解析动辄 100 多兆的高精度的多媒体文件，有些硬骨头 5~10 分钟都啃不完。不仅如此，真出了重大故障引发系统大乱，一条没办完的任务没准要挂到明天早上才能人工恢复。到时候早就经过好几个10分钟了，Redis 数据八成已经被自动淘汰，甚至机器连夜维修导致缓存被全清空了。如果这时候这批 PDF 又被误推倒了队列前，没了 Redis 的防重挡箭牌，几百篇长文就会毫无拦阻地全在后台一堆机器上又狂跑一天，浪费极其昂贵的GPU算力费。只有老老实实地落到 MySQL 持久化账本里，才是钢铁保障！

Redis 去重机制很适合那种没什么要求、丢一笔两笔不心疼的超轻量场景，但咱们这个系统面临太多约束：

1. 它解决不了“库里业务数据建好了，消息却发送挂了”的刚性丢失问题。
2. 它缺少有效的分布式并发“防冲突争抢”设计，有 key 只能代表发过，无法追踪业务完成度。
3. 如果处理周期一旦变长拉远，或者要求系统停留在失败状态可追责复盘，这就不仅仅是数据有没有到期（TTL）的问题了。
4. 由于 AgenticRAG 领域本身就面临极高的大模型算力消耗等高额副作用账单。

所以为了省钱求稳，这套被选择的“企业级安全处理恢复流程”是一项必需的基础建设，绝不能用轻飘飘的缓存做点技巧应付过去。

## 9. 这四类消息链还分工吗？

> **真实场景例子**：
> 下列四个 Topic，每一个都像是流水线里的一个精密车间，我们之所以分开，就是好让各管一段、防止“一死到底”。你只有弄明白每一步到底是干啥、以及重了该去哪，下次线上看到日志卡在一半报大错时，才知道应该去修哪里。

| Topic名 | 做什么活儿？ | 重复了怎么防？ | 真走不通了怎么丢出处理 |
| --- | --- | --- | --- |
| `doc-parse-request` | 读入源文件，请求外接程序或算法解析得好文本 | 绝不允许重复，保证只能有一位得胜者进行此项长耗时工作 | 重试无果送进 `doc-dlq` |
| `doc-vectorize-request` | 切分成细块，调大模型打上数学向量并进 ES | 本身机制拦一遍防重，另外 ES 写之前也要删旧记录防重 | 重试无果送进 `doc-dlq` |
| `doc-delete-request` | 清理 ES 里那海量的遗留分块/向量数据并且把任务终结 | 若确实执行还一遍则安静跳过当做无事发生，绝不多余报错 | 重试无果送进 `doc-dlq` |
| `doc-dlq` | 将救不活的消息打包、打上标记停在这里静待人工救援 | 拦住报错本身防止疯狂地在后台不停死循环刷库落记录报警 | 通知程序员起来排查并重开通路 |

### 9.1 `doc-parse-request` 这个步骤

> **真实场景例子**：
> 就是打头阵的。负责把张三满是花样格式的破文件塞给 MinerU 之类的工具，提炼出干干净净包含了段落与表格的 JSON。这个活做完就完事，它若是中途多点触发也坚守本职：绝不去掺和后面的写库算向量，省的重复劳动导致数据重叠串味。

1. 干什么：作为后台慢慢啃文件的入口点。
2. 何时发起：上传一完成立刻扔进本地消息表(Outbox)里进行后台发放，别卡着前端界面转圈就行。
3. 身上带什么粮草（载荷）：它得能带上：要处理谁（`documentId`）、哪家的所属（`tenantId`）、文件位置到底在哪儿呀、以及用来标记这是哪头跑的一段专属跟踪码。
4. 它具体做啥子事：专职且仅专职把源文件给翻译好；绝不允许瞎插手管向量的事情。
5. 写完要交接什么：如果成功跑完了，必须立马丢包——产生另一个名叫 `doc-vectorize-request` 的通知，去让后面接手接着跑。
6. 出了岔子啥样：如果报错了几次死活不行，去 `doc-dlq`。

### 9.2 `doc-vectorize-request` 这个步骤

> **真实场景例子**：
> 接力第二棒。刚才那干干净净的 JSON 现在拿到手里了不当白纸浪费。它在这把它切成五百块肉（Chunk），往这五百块肉里头调大模型打好独属于它属性的向量码，随后入到 ES。如果你在打到200块肉的时刻服务器崩掉了？由于上个环节没发出完成消息，一会儿这个系统再次重发这段干活指令时，系统第一件事必须是要——进 ES 把上回这可怜的 200 块碎渣删的一点不许留！再从第 0 块重头开始写入。

1. 干什么：接上一棒的工作，负责切分、去算大模型向量并且最后落在存储搜索结果里。
2. 何时发起：当头阵“解析”阶段说搞定了抛过来即可。
3. 身上带什么粮草（载荷）：文档自身ID、租户编号外，还得明确写出了上一棒解析出的新地址、权限标、这批信息要去哪个具体知识库（`kbId`）。
4. 它具体做啥子事：切分计算向量完结后把任务标识变成总完结态。
5. 怎么在业务上挡刀防重：若文档状态早显示已经是向量化完（`VECTORIZED`）或正被别人死死占着（`PARSING`），那别管你怎么收的通知也别干。并且写入新片段必须首先做：删除同记录所有的老分片。
6. 出了岔子啥样：跟前头一样，连着试错多次只好把这棘手残次品留给 DLQ 死信库让维护人员收拾摊子。

### 9.3 `doc-delete-request` 这个步骤

> **真实场景例子**：
> 小张由于眼花把自己珍贵的内部文件误在网页给点删了。由于底层为了快，数据库当时就被“咔嚓”删干净了。这个时候，要保证在外面展示界面的 ES 这里头的大批量零碎的数据也被完全顺带干掉才算安全，如果不巧，删这批零碎片儿时系统发了四趟删的破通知——头一个节点刚删彻底，接着另外哥几个节点一看“呀？这 ES 本来就已经找不到这条东西了呀！我直接报绿灯写完工不就得了！”

1. 干什么：对刚才所干的好事的痕迹从里到外擦掉的收尾收容中心。
2. 何时发起：业务点完网页版删除按钮立即落好本地待办事实之后。
3. 身上带什么粮草（载荷）：你得给人家租户数据，这种带“删除”功能的绝对不能“大搞株连”，没特定条件不允许强删。
4. 怎么业务防重：这步最天然耐造，被连着下5遍“你给老子删老子！”的指令也不会重复冒新的系统残次物，删了就删了呗。真碰上重复通知一视同仁看作处理好直接点赞放行即可。

### 9.4 `doc-dlq` 这个步骤

> **真实场景例子**：
> 文件乱码、网络彻底断死、或者程序爆出 NullPointer 的致命缺陷。当那些重试了好几次依然头铁去送死的通知如果连绵不断地在这里耗着死死运转刷空算力卡库资源时怎么解？把这堆垃圾统统“集中到”隔离病房（DLQ 死信处理区）放好，记录好当时的案发现场环境。开发哥哥们明早上班，泡上一杯茶点开控制台：修补掉破漏算法重启节点，然后拿着管理钥匙点击重发，把任务直接推回原跑道里这才是正解止损姿势。

1. 干什么：最后一道也是专门给系统善后并停止继续无限错误耗血的最后病房门。
2. 何时进去：只有超过规定退避极限还在不停撞墙的人会被赶来。
3. 它干嘛呢：不再重复运行任何耗算力的破程序，就只安安静静地做这三步：集中错误登记入库归档、找清错误缘由并且敲锣打鼓留告警报平安。
4. 怎么在业务重防重：得小心连这里的防死信流程它自个如果都被短时间同个人轰炸重复通知也不行啪。重复写错误也是不小的一笔日志灾难开销。
5. 退出的手段：人工介入或触发回放程序重新给推入正轨继续循环而不是这里边瞎重试强转。

## 10. 这两套老在记账的破东西有什么区别与要求？

> **真实场景例子**：
> 人们总觉得“既然那账本记录了你文件在处理中为什么还要留一个锁说这个消息在占用中呢？这不浪费吗？” 事实是，任务生命周期负责大方面长远的进展汇报反馈进度条＋而消息锁关注目前眼前这条信息它有没有被同级别的其他接收机器并发抢走导致大闹后台乌龙事件。

不要把追踪业务宏观周期的 `document_async_task` 和只管消费过程中的 `mq_consume_log` 的用途给搅在一块：

1. `document_async_task` 专门用于说明长流程现在的整个进度的汇报；
2. `mq_consume_log` 用于盯紧当前微观这条特定信息消费的状态轨迹到底有没有其他人跟你干重复活。

所以这两者一定有固定先来后到的协同纪律，严禁调换错次：

1. 一定得先拿到独占的“这个我先占用”锁（认领这事儿归你了才行！）。
2. 被占用后你去改业务账本那上面的 `RUNNING` 说此事务目前进行中了。
3. 真正折腾完出活或者是真的彻底废掉了时才再去填写该任务最后结论是出圈了还是跳过拉倒 `SUCCEEDED/SKIPPED/FAILED`。
4. 把各路全忙和完结干净后才能拍个手动“消息已彻底确认并消费”按钮。

不能前人后人互换这顺序。

## 11. 我们咋搞运维盯好这底线呢

> **真实场景例子**：
> 系统一旦全面大投产，没监控这跑的好坏谁也没谱。最怕的情况已经不再是它报不报错报错丢没丢，最担心是背地在重复搞活费神却没谁晓得。于是咱们专门提列了几条盯紧防线的点子。

1. 用好自带身份的 `messageId` 把它的来龙去脉从前台追踪至各分布式组件里，不用去死命求助于那串哈希随机出来的破串儿。
2. 日常得去看三种死盯住别憋爆的东西堆高高：Outbox发送有没给死憋、处理出问题多不多、和那个被扔到急救死信 DLQ 区里的人爆多没？
3. 注意咱们花钱重来费用的两大心病点“抢冲突率（多台服务器挤在一处死抢一件活的比例）",以及跑完之后还在一直徒劳通知重做而被挡出来的占比——也就是常说的命中 `ALREADY_COMPLETED`。
4. 给值钱的链路上多加上一条在极端事故也能彻底恢复重新找回来、发出来再次过一手的后盾支持！
