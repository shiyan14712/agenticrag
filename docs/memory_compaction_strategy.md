# Agentic RAG: 层级滑动窗口内存压缩策略

## 上下文窗口挑战

在复杂的 Agentic RAG 工作流中，往往涉及多次文件读取、Shell 命令执行以及持续的用户与智能体交互，这会导致对话上下文呈线性增长。如果采用简单的截断方法——即当达到上下文限制时直接丢弃最旧的消息——将导致灾难性遗忘。

如果模型忘记了任务开始时的指令，或者忘记了几轮迭代前重要的文件读取结果，工作流就会陷入死循环或失败。

## 解决方案：行业领先的滑动窗口内存机制

为了在精确度、Token 成本和无限记忆持久性之间取得平衡，我们将三层内存架构从死板的阈值截断模型，转变为**弹性滑动窗口滚动压缩**模型。

### 1. Redis 与 MySQL 存储策略
我们严格分离了快速、可变的运行状态，与不可见、仅追加的历史记录。

* **Redis（活跃工作集）**
  * **存储内容：** 原始滑动窗口消息（L1）、滚动叙事摘要（L2）以及高度提炼的状态/事实（L3）。
  * **原因：** 在 Langchain4j 会话轮次中需要高频读写。Redis 维护了我们在下一轮需要注入 LLM 的精确上下文向量。
* **MySQL（永久审计与长期单一真实数据源）**
  * **存储内容：** 每一条原始的 `ChatMessageDO`（仅追加），以及带有当前 `compression_level` 的标记。全局 L3 摘要也会同步到会话表的 `summary` 字段。
  * **原因：** 支持完整的对话审计、向用户展示的会话历史回放，以及离线后台再训练。

---

## 3 层滑动窗口架构

### 第一层 (L1)：活跃滑动窗口
* **触发机制：** 由 `application.yaml` 中的 `l1-limit` 控制。
* **动态而非固定：** `l1-limit` 并不意味着“截断死亡线”。相反，它表示活跃滚动缓冲区的最大容量。
* **滑动行为：** 当 `L1_size > l1-limit` 时，窗口发生滑动。超出限制的、最旧的消息（例如刚刚跌出窗口的 2 条最旧的消息）将从 L1 中“驱逐”，但**不会被永久丢弃**。它们会立即传递给 L2 摘要引擎。

### 第二层 (L2)：滚动叙事摘要
* **压缩策略（中期）：** L2 并不是批量汇总巨大的文本块，而是作为**滚动摘要**运作。
* **过程：** `新 L2 = LLM_Summarize(当前 L2 + 新驱逐的 L1 消息)`。
* 这为工作流提供了连续的叙事脉络。LLM 无缝地将刚刚驱逐的技术细节（如最近完成的工具执行记录）融入到现有的中期叙事中。

### 第三层 (L3)：长期核心事实与提炼
* **触发机制：** 由 `l2-limit` 控制。当 L2 吸收的消息量超过 `l2-limit`（通过 Redis 中的滑动计数器追踪）时，意味着叙事变得过于啰嗦并且跨越了太多不相关的话题。
* **压缩策略（持久化提炼）：**
  * 我们执行深度的结构化提取：`新 L3 = LLM_Distill(现有 L3 + 当前 L2)`。
  * L3 的提示词专门针对**持久性事实、核心实体和关键的全局用户决策**，并明确丢弃短暂的对话噪音或调试循环。
  * **提炼后：** L2 的滚动计数器重置，系统保留刷新后轻量级的 L2 叙事环境继续运行，而 L3 持久保存着长期的知识矩阵。

---

## 为什么这种策略优于简单截断？

1. **信息连续性：** 早期的发现或指令绝不会被严格意义上地“丢失”。它会平滑地向下层级联——从原始字符串（L1） -> 演变为叙事句子（L2） -> 最终固化为永久的事实画像（L3）。
2. **上下文窗口稳定性：** 注入的系统上下文 (`L3 + L2 + L1`) 在算法上是有边界的。无论用户进行 10 轮还是 10000 轮对话，LLM 始终会收到受控的、高密度的负载，而绝不会触碰 `max_tokens` 限制。
3. **弹性容灾：** 如果 Redis 节点重启，通过对 MySQL `compression_level` 跟踪可以优雅降级，允许系统精准地从之前离开的状态来追溯重构滑动窗口。
